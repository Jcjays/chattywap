# Architecture

## Style

Chattywap is a **modular monolith**: one Spring Boot application (Java 21, Spring Boot 4.1, Maven), one PostgreSQL database, one RabbitMQ broker. Code is organized **by feature**. Each feature package owns its entry points, business rules and persistence. There are no microservices, no CQRS, and no extra "clean architecture" layers.

## Packages

Root package: `com.adonis.chattywap`. `ChattywapApplication` stays in the root package so component scanning covers every feature.

```
com.adonis.chattywap
├── ChattywapApplication.java
├── auth/           authentication, token issuing/validation, Spring Security configuration
├── user/           user profiles and user lookup
├── conversation/   conversations and their membership
├── message/        message persistence and operations, delivery/read receipts
├── presence/       online/offline state and presence operations
├── realtime/       WebSocket/STOMP configuration, CONNECT authentication, STOMP entry points, outbound delivery
├── messaging/      RabbitMQ configuration, event publishing and consuming, transactional outbox
└── common/         shared exceptions, API error handling, genuinely cross-cutting code
```

There is no top-level `config` package. Configuration lives with the feature it configures: security in `auth`, STOMP in `realtime`, RabbitMQ in `messaging`.

### Inside a feature

Features are flat by default. Add a `dto/` subpackage once a feature has DTOs. Add other subpackages only when a feature grows large enough that they clearly help.

```
conversation/
├── ConversationController.java
├── ConversationService.java
├── ConversationRepository.java
├── Conversation.java
└── dto/
```

These names show where each responsibility goes. Classes are created when a feature needs them, not ahead of time.

## Layers

| Layer | Responsibility |
|---|---|
| Controller / STOMP handler | Transport only: bind and validate input, identify the caller, call a service, map the result to a DTO. |
| Service | Business rules and authorization (e.g. "only members may post to a conversation"). Owns transaction boundaries and publishes domain events. The only entry point other features may call. |
| Repository | Spring Data interface for the feature's own tables. Package-private where possible, so only the owning feature can reach it. |
| Entity | JPA mapping of a table the feature owns. Never leaves the feature. |
| DTO | Records for request, response and event payloads. Request DTOs carry Bean Validation constraints. |

## Dependencies and boundaries

Allowed dependencies between packages:

| Package | May depend on |
|---|---|
| `common` | nothing in the application |
| `user` | `common` |
| `auth` | `user`, `common` |
| `conversation` | `user`, `common` |
| `message` | `conversation`, `user`, `common` |
| `presence` | `user`, `common` |
| `realtime` | `auth`, `message`, `conversation`, `presence`, `user`, `common` |
| `messaging` | `realtime`, `message`, `conversation`, `presence`, `user`, `common` |

The graph must stay acyclic. A new edge is fine if it keeps the graph acyclic; update this table in the same change.

Where a feature needs something from a feature that depends on it, it declares an interface and the other feature implements it, instead of adding the reverse edge. The only case: `conversation.UnreadMessageCounter`, which `ConversationService` calls for the conversation list's unread counts and `message.UnreadMessageCounts` implements (decision 19).

Rules:

1. Controllers and STOMP handlers contain no business logic.
2. Controllers and handlers never use repositories; they call services.
3. Services enforce business rules and authorization. A check made only in a controller or interceptor does not count.
4. Entities are never exposed in REST responses, STOMP payloads or RabbitMQ messages. The owning feature maps them to DTOs.
5. Features call each other only through services, using DTOs and IDs. No feature uses another feature's repository or entity.
6. An entity refers to another feature's entity by ID, not by JPA association.
7. RabbitMQ consumers deserialize the payload and delegate to a service (or to `realtime` for delivery). They contain no business logic.
8. Code goes into `common` only when two or more features genuinely need it. `common` never depends on a feature.
9. Spring components use constructor injection: `final` fields, one constructor, no field `@Autowired`.
10. No generic base controllers, base services, base entities, or generic CRUD abstractions.
11. No microservices, CQRS, or additional architectural layers.

## Where infrastructure belongs

**REST (Spring MVC)**: controllers in `auth`, `user`, `conversation` and `message` (e.g. message history). The `@RestControllerAdvice` that maps exceptions to HTTP errors lives in `common`. The `SecurityFilterChain` lives in `auth`.

**STOMP / WebSocket**: only `realtime`. It holds the endpoint and broker configuration, the CONNECT interceptor (validates the token via `auth`), subscription authorization (decided by the owning service), `@MessageMapping` handlers that call `message`, `conversation` and `presence` services, connect/disconnect listeners that update `presence`, and outbound delivery to connected users, of events stored on its own instance and of those `messaging` brings from the others (decision 26). No other package uses STOMP types or `SimpMessagingTemplate`.

**PostgreSQL**: each table is owned by exactly one feature, and its entity and repository live in that feature. The outbox table belongs to `messaging`. Flyway migrations in `src/main/resources/db/migration` are the only way the schema changes; Hibernate never generates it.

**RabbitMQ**: only `messaging`. It holds exchange/queue/binding configuration, the outbox relay, `@RabbitListener` consumers, and the fan-out of live deliveries between instances (decision 26). No other package imports Spring AMQP.

**Event flow**: a feature publishes a domain event (a record in its `dto/` package) with Spring's `ApplicationEventPublisher`. `messaging` listens inside the publishing transaction and writes the matching integration event (a record in `messaging/dto/`) to the outbox, so the change and its event commit together. The relay publishes outbox rows to RabbitMQ, and consumers hand them to services or to `realtime`. Because features never depend on `messaging`, this flow creates no cycle (decision 15).

`realtime` also listens to domain events directly, after the publishing transaction has committed (`@TransactionalEventListener`), and delivers them to the clients connected to its instance: immediate, best-effort WebSocket delivery that doesn't depend on RabbitMQ. The first such event is `message.dto.MessageSentEvent` (decision 14); `message.dto.ReceiptPositionChangedEvent` is the second (decision 20). `messaging` passes the same events, after the commit, to the other instances through RabbitMQ, outside the outbox, and hands those it receives from them to `realtime`, which delivers them to its own clients (decision 26). Consumers of the outbox's events never deliver them over WebSocket again. A domain event gets an integration event in the outbox only when a consumer needs it: receipt changes have none.

## Configuration and test infrastructure

- Connection settings and secrets come from environment variables (`POSTGRES_*`, `RABBITMQ_*`, `JWT_*`) and are referenced in `application.yaml`. Committed configuration holds no credentials; the only committed key is the test-only JWT secret in `src/test/resources/application-test.yaml`. For local development, the values live in an uncommitted `.env` file that Docker Compose reads and the application imports (`spring.config.import`). Real environment variables take precedence.
- `compose.yaml` runs PostgreSQL and RabbitMQ for local development. The application runs on the host.
- Unit tests (`*Test`, `*Tests`) run with Surefire in `mvn test` and need no external services. Integration tests (`*IT`) run with Failsafe in `mvn verify` and get PostgreSQL and RabbitMQ from Testcontainers (`TestcontainersConfiguration`, wired with `@ServiceConnection`). The test profile turns the scheduled outbox relay off, so that nothing publishes or consumes in the background of other tests; tests of the relay run it themselves, and `BrokerOutageIT` turns it on. `MultiInstanceDeliveryIT` starts two applications itself, without Spring's test support, against one PostgreSQL and one RabbitMQ container (`TestcontainersConfiguration.postgres()`, `rabbitMq()`).
- Actuator runs on a separate management port (`MANAGEMENT_PORT`, bound to `MANAGEMENT_ADDRESS`) with health details, metrics and Prometheus; the application port serves only the probes `/livez` and `/readyz` (decision 22). Tests give the management server a random port.
- Cross-cutting HTTP filters live in `common`: request IDs and request logging (`RequestLoggingFilter`, decision 21) and the request body limit (`RequestBodyLimitFilter`, decision 25). The filter that adds the caller to the log context belongs to the security filter chain, in `auth`.
- Operational documentation: [OPERATIONS.md](OPERATIONS.md) (configuration, health, metrics, logs, runbook). Load tests and their results: [loadtest/README.md](loadtest/README.md).

## Decisions

1. **Token format**: access tokens are self-contained JWTs (HS256, 15 minutes), issued with Spring Security's `JwtEncoder` and validated by its OAuth2 resource server support (`spring-boot-starter-security-oauth2-resource-server`) with a `JwtDecoder` that checks signature, expiry, issuer and audience. Refresh tokens are opaque random strings, stored as SHA-256 hashes in PostgreSQL, single-use and rotated on every refresh. Each login starts a token family (`refresh_token_families`); reusing a rotated token revokes the family. Every refresh and logout locks the family row first, so the operations of one session are serialized.
2. **Caller identity**: the JWT subject is the user ID. Controllers take Spring Security's `Authentication` as a parameter and read `Authentication#getName()`, so they depend on Spring Security, not on `auth`.
3. **Credential ownership**: the password hash is a column of `users`, owned by `user`. `auth` hashes passwords (it owns the `PasswordEncoder`) and passes only hashes to `UserService`, which hands them back for login as a `UserCredentials` DTO. `UserService` normalizes emails (trim, lower case), and a check constraint keeps the stored form normalized.
4. **Errors**: REST errors use RFC 9457 problem details. Feature exceptions extend Spring's `ErrorResponseException`, so the handler in `common` maps them without knowing any feature. Security failures (missing or invalid access token) are answered in the same format by an entry point in `auth`, because they happen in the filter chain, before Spring MVC.
5. **IDs**: tables use UUID primary keys, generated by Hibernate. The exception is `outbox_events`, whose ID is the event ID: the application generates it, because the serialized payload contains it before the row is inserted.
6. **Direct-conversation uniqueness**: a direct conversation stores its two participants on its own row (`direct_user1_id < direct_user2_id`, in PostgreSQL's unsigned UUID order) under a unique constraint. A request that loses a creation race catches the violation and reads the winner's conversation in a new transaction.
7. **Group changes**: adding, removing, leaving, promoting, demoting, renaming and deleting lock the conversation row first (`SELECT ... FOR NO KEY UPDATE`), so changes to one conversation are serialized. Sending a message takes the same lock, in any conversation (decision 12). This keeps memberships unique without failed inserts, and lets the member limit and the "an active group has an administrator" rule rely on what they read: a count read after the lock can't be outdated by a concurrent change. New rules about a group's members or roles must take the same lock.
8. **Member limit**: at most 100 members per group, the creator included, defined once as `ConversationService.MAX_GROUP_MEMBERS` and checked by the service under the lock from decision 7. It isn't repeated as a database constraint, which would need a stored member count or a trigger. A request that would exceed it adds nobody (`409`).
9. **Group lifecycle**: deleting a group, or its last member leaving, removes its memberships and sets `conversations.deleted_at` in one transaction (soft delete). The row stays so that rows referring to the conversation, such as future messages, don't need `on delete cascade` or become orphans. Memberships are what grant access, so removing them makes a deleted group unreachable through the same membership checks every request already makes; queries also filter on `deleted_at`. Direct conversations can't be deleted (check constraint).
10. **Conversation-list pagination**: the order `updatedAt desc, id desc` (most recent activity first, decision 12) is total because the ID is unique. Besides page numbers (kept for compatibility), the list supports keyset pagination with an opaque cursor that encodes the last entry's `(updatedAt, id)`. Cursors avoid the shifts that inserts, deletes and moves cause in offset pagination. They don't provide a snapshot: each page reads the current data. The cursor encoding (`KeysetCursor`) and the page metadata live in `common`, because message history uses the same pagination.
11. **Message ordering**: a conversation's history is ordered by `created_at`, then by ID, newest first; the unique ID makes the order total and the same on every request. `created_at` is a timestamp, not a sequence number: the application's clock, truncated to microseconds, read after the send has taken the conversation lock (decision 12). Messages of one conversation are therefore stored one after the other, and with one clock that doesn't go back, a message that commits later has a later `created_at`: the history order is the commit order. That is a consequence of the lock, not a guarantee: with several application instances whose clocks differ, or a clock that is set back, a message that commits later can sort below one that was already visible, possibly within a page a client has already loaded. Messages stored in the same microsecond are ordered by their random IDs. History pages like the conversation list (decision 10); a cursor page compares `(created_at, id)` as one row value, so PostgreSQL starts its index scan at the cursor. Messages also have a per-conversation sequence number (decision 17), which receipts use; the history keeps this order.
12. **Activity on a member's behalf**: other features check access to a conversation through `ConversationService`: `requireMembership` to read, `recordActivity` to write. `recordActivity` takes the conversation lock from decision 7 (checking membership before and again after it), moves the conversation's `updated_at` to now and returns that time, which the caller uses for what it stores (the message's `created_at`). It requires the caller's transaction (`MANDATORY`), so the activity time and the message commit or roll back together, and the lock lasts until the message is stored: leaving, removal and group deletion wait for it, and a send that comes after them is rejected. A message is therefore never stored after its sender lost access. Taking the conversation lock first, the same order as every group change, also rules out deadlocks between sends and group changes; a send that locked anything else first and then updated the conversation row could deadlock with a removal. The cost: sends to one conversation run one after the other, and wait for group changes in progress; on each instance they also wait for each other before taking a database connection, so that a busy conversation can't occupy the whole pool (decision 23). `updated_at` is the conversation's activity time: the last change to it or its newest message. The conversation list is ordered by it. It has no index, so the frequent updates touch no index and can be HOT updates.
13. **STOMP authentication**: clients connect to `/ws` (plain WebSocket) and present the access token in the STOMP CONNECT frame as `Authorization: Bearer <token>`. The HTTP handshake is public (only `GET /ws`); `auth` ignores an `Authorization` header on it, so the CONNECT frame is the one place a token counts. `realtime.StompSecurityInterceptor`, on the client inbound channel, validates the token with Spring Security's `JwtAuthenticationProvider` and the `JwtDecoder` bean from `auth` (the rules REST uses), sets the resulting `JwtAuthenticationToken` as the connection's user, and removes the header from the frame. STOMP handlers take `Authentication` and read `getName()`, like controllers (decision 2). The interceptor denies by default: CONNECT, SUBSCRIBE to `/topic/conversations/{id}/messages`, `/topic/conversations/{id}/receipts` and `/user/queue/errors`, SEND to `/app/conversations/{id}/messages`, UNSUBSCRIBE, DISCONNECT and heartbeats; SUBSCRIBE and SEND re-validate the token, so a connection can't act after its token expired. Subscription authorization is decided by `ConversationService.requireMembership`, send authorization by `MessageService` (rule 3). Rejections are ERROR frames with problem-detail bodies, sent by the interceptor itself (frames are processed in order, decision 14, and Spring's ordering decorator swallows exceptions from interceptors); the connection is closed. Spring closes it right after the ERROR frame, and its session decorator discards frames still queued for a connection that is closing, which loses the ERROR frame when another frame to the same connection is being written at that moment; `realtime.FlushBeforeCloseSessionDecorator`, every connection's session, makes closing wait until the frames sent before have been written.
14. **Real-time delivery**: Spring's simple in-memory broker (`/topic`, `/queue`, user destinations under `/user`) on every instance; clients connected to other instances receive the events through RabbitMQ (decision 26). `MessageService.sendMessage`, the one path for REST and STOMP sends, reads the conversation's members under the conversation lock and publishes `MessageSentEvent` (the stored message and those members as recipients). `realtime.MessageBroadcaster` delivers it after the commit to `/topic/conversations/{id}/messages`, naming the recipients' STOMP sessions in an internal header; `realtime.RecipientSessionsInterceptor` on the client outbound channel drops the message for every other subscription, so a subscription that outlived its user's membership receives nothing. Delivery is at most once and best effort; the history is the record, and clients catch up from it after reconnecting. Frames from one connection are processed in order, on the thread that read them (decision 24), and messages to one connection are sent in publish order (`preserveReceiveOrder`, `preservePublishOrder`), so one client's messages are stored and delivered in the order it sent them. Errors of a STOMP send go to the sending connection on `/user/queue/errors` as problem details.
15. **Transactional outbox**: `messaging.OutboxWriter` turns `MessageSentEvent` into a `messaging.dto.MessageCreatedEvent` (version 1, IDs only, no content) and inserts it into `outbox_events` while `MessageService.sendMessage` is still in its transaction (`@EventListener`, `MANDATORY`): the message and its event commit together or not at all, and nothing in the transaction talks to RabbitMQ. `messaging.OutboxRelay` polls on its own scheduler thread (`outboxRelayScheduler`, so it neither waits for nor delays the WebSocket broker's tasks). Each batch is claimed in one short statement (`update ... where id in (select ... for update skip locked) returning *`) that counts the attempt and moves `next_attempt_at` past a lease; no lock or transaction is held while publishing. Events go to the durable topic exchange `chattywap.events` as persistent, mandatory messages with correlated publisher confirms; only an acknowledgement for a message that wasn't returned marks the event published. Nacks, returns, confirm timeouts and connection failures keep the event pending with `last_error` and a delay that doubles per attempt up to a maximum; events are retried indefinitely and never dropped. A batch ends before its lease: sending stops at the first failed send and once only the confirm timeout is left, and a failure is recorded only if the event's attempt count is still the claim's, so a relay whose lease expired can't move another relay's lease. The relay publishes on a connection of its own, so a broker that blocks publishers doesn't block consumers' acknowledgements. A lease that expires (the relay stopped mid-batch) makes the event due again, so a crash after the broker's confirmation but before the database update publishes it twice: delivery is at least once. The relay's times are PostgreSQL's `now()`, so instances agree on leases; events have no guaranteed order. Polling was chosen over CDC (no extra infrastructure) and over publishing after the commit from the request thread (which would lose events on a crash between commit and publish).
16. **Consumers and idempotency**: one durable quorum queue per consumer, bound to the routing keys it handles, with a per-consumer dead-letter queue behind the direct exchange `chattywap.events.dead-letter`. The container acknowledges after the listener returns (`acknowledge-mode: auto`) and never requeues a rejected message (`default-requeue-rejected: false`). Failures are retried in the listener with exponential backoff (`spring.rabbitmq.listener.simple.retry`), except invalid events, unreadable payloads and data integrity violations, which fail the same way every time (`MessagingConfig.isRetryable`); after that the message is rejected and the broker dead-letters it. The quorum queue's delivery limit dead-letters a message that keeps crashing the consumer before it can reject it. Dead-lettering is at least once (`x-dead-letter-strategy`, which needs `reject-publish` overflow), so a dead letter isn't lost if the dead-letter queue can't take it at once. Consumers deduplicate by event ID in `processed_events (consumer_name, event_id)`, inserted with `on conflict do nothing` in the same transaction as their effect, so a redelivery or a republished event changes nothing, and a crash between the two leaves neither. The example consumer (`MessageCountConsumer` → `MessageCountService`) counts events per conversation in `conversation_message_counts`, an effect whose duplicates would be visible; nothing in the API reads it. Processing is therefore effectively once per event in PostgreSQL, but delivery stays at least once; effects outside the database (push notifications, later) can't be made exactly once this way.
17. **Message sequence numbers**: `messages.sequence_number` numbers a conversation's messages from 1, without gaps. `MessageService.sendMessage` assigns the highest number plus one, read after `recordActivity` took the conversation lock (decision 12): no other message of the conversation can be stored until the commit, so the number is free, and the numbers follow the commit order on any number of instances, whatever their clocks say. A rolled-back send uses up nothing, and messages are never deleted, so there are no gaps. `unique (conversation_id, sequence_number) include (sender_id)` catches a number assigned twice; its index also serves the highest number (one entry, read backwards) and unread counts (index-only, decision 19). V6 numbered existing messages in history order. The number is in `MessageResponse` (`sequenceNumber`), so clients can tell whether they have every message up to one, which delivery acknowledgements rely on (decision 18). The history keeps its order by `(created_at, id)` (decision 11); on one instance both orders are the same. Receipts don't use that order because a position in it can be passed by a message that commits later with an earlier time (several instances, a clock set back), which would then never count as unread. Cost: one more statement per send.
18. **Receipts as per-member positions**: `receipt_positions` (owned by `message`) has one row per member who has acknowledged anything: the last message their client acknowledged receiving and the last one they reported reading, as sequence numbers, with the times the positions last moved. A position covers every message up to it; acknowledgements are cumulative ("I have every message up to n"), never per message, so the two models aren't mixed. One row per message and recipient would be up to 99 rows per message in a full group, written for every message whatever anybody reads, and would need its own cleanup; positions are one row per member, written only when they move. Reading implies delivery: a read moves the delivered position up to it, and a check keeps `read <= delivered`. The client identity is the token's; membership is checked first (non-members get the conversation's `404`), then that the message is the conversation's (`404`, `Message not found.`). Each change is one upsert that only moves forward (`insert ... on conflict do update ... where old < new`), so retries, duplicates and outdated requests change nothing and publish nothing, and concurrent ones wait for each other's row lock and the furthest wins. Acknowledgements don't take the conversation lock and don't wait for sends. A member removed between the membership check and the upsert fails on the foreign key to `conversation_members` and gets the same `404`; that foreign key also removes the row with the membership (cascade). (Removed and added again in between, the position lands in the new membership.) Times come from the application's clock, taken before the upsert may wait for the row, so the upsert keeps them from moving back: a time is never earlier than the one it replaces, and a read time never earlier than the stored delivered time. Two more foreign keys make sure positions name messages of the same conversation. Synchronous: the position is stored when the request returns; nothing goes through RabbitMQ. Every member of a conversation can see every member's positions (`GET .../receipts`), in groups too.
19. **Unread counts**: computed when asked, from the messages and the read positions, never stored: the messages others sent with a sequence number after the member's read position, or all of them without one. Nothing can drift, so retries, duplicates and the order in which messages and read updates commit don't matter, and there is nothing to reconcile. With a read position, the count reads the index from the position on (index-only, the unread entries only); without one, all the conversation's index entries. The conversation list needs the counts too, but `conversation` can't depend on `message`: `conversation.UnreadMessageCounter` declares what `ConversationService` needs and `message.UnreadMessageCounts` implements it. `UnreadMessageCounts` depends only on its repositories, so there is no bean cycle with `ConversationService`, and it is also what `GET .../unread-count` uses, so both report the same. A page takes at most two statements for its counts: conversations with a read position, and those without.
20. **Real-time receipt changes, no outbox events**: `ReceiptService` publishes `ReceiptPositionChangedEvent` (the member's position and the conversation's members at that moment) only when a position moved. `realtime.MessageBroadcaster` delivers it after the commit to `/topic/conversations/{id}/receipts`, through the same recipient filter as messages (decision 14); members subscribe like to the messages topic. Unlike a send, the recipients are read without the conversation lock, so a member removed while the change commits can still receive it; the messages it covers were all sent before the removal. Delivery is best effort; `GET .../receipts` and `GET .../unread-count` are the record. Receipt changes write no integration event: nothing consumes them asynchronously, an event with no queue bound to its routing key would be returned by the broker and retried indefinitely by the relay (decision 15), and a queue nobody consumes would grow without bound. A consumer that needs them later (push notifications that clear once read) adds a versioned event in `OutboxWriter`, like `MessageCreated`. Unread counts aren't pushed: keeping every recipient's count current would cost one count per member and message. Clients add the messages they receive and recompute from their own receipt changes, and fetch the counts after reconnecting.
21. **Request IDs, logs and metrics**: every HTTP request and every STOMP frame gets a request ID (`common.RequestLoggingFilter`, `realtime.StompLogContextInterceptor`; a proxy's valid `X-Request-Id` is kept), which is in the log context (SLF4J MDC, `common.LogContext`) with the caller's user ID while it is handled, and in the `X-Request-Id` response header. `messaging.OutboxWriter` stores it with the events the request writes (`outbox_events.correlation_id`, V8), the relay publishes it as the AMQP `correlation_id`, and consumers put it, with the event ID, into their log context (`messaging.EventLogContext`): an asynchronous effect leads back to its request. Not part of the event contract. Logs carry IDs, statuses and causes, never credentials, tokens or content; structured JSON output is Spring Boot's (`LOGGING_STRUCTURED_FORMAT_CONSOLE`). Requests are logged when they fail with a server error or are slow, others at `DEBUG` only, so log volume follows problems, not traffic. Metrics are Micrometer's, exported for Prometheus; tags have small fixed value sets, never user, conversation, message or event IDs, which belong in the logs. Each feature registers its own (`chattywap.outbox.*`, `chattywap.events.*` and `chattywap.fanout.*` in `messaging`, `chattywap.websocket.*` and `chattywap.stomp.*` in `realtime`). No tracing system: the request ID is enough to follow one operation through one application.
22. **Health and readiness**: actuator endpoints live on a separate management port; access to it, kept off the public network, is the authorization (the security filter chain applies there too and permits only exposed endpoints; with the management port equal to the application port, every actuator path is refused). The application port serves only `/livez` and `/readyz` (Spring Boot's probe groups as additional paths), which answer with a status and nothing else. Liveness contains only the application's own state. Readiness contains only "started and not shutting down", deliberately neither PostgreSQL nor RabbitMQ: both are shared by every instance, so removing instances from the load balancer helps no request, and a database check during pool exhaustion would remove every instance at once. Dependency status is in `/actuator/health` on the management port, for monitoring and alerting. The probe groups state their members explicitly: a configured group otherwise includes every indicator.
23. **Send gate per conversation**: `message.ConversationSendGate` lets two sends per conversation at a time, per instance, start their transactions; the others wait in memory without a database connection, up to `chattywap.messages.send-wait-timeout` (then `503`, `ConversationBusyException`). Measured without it: 50 concurrent senders to one group left all 10 connections waiting for that group's row lock, and unrelated reads went from 5 ms to 575 ms at p95. Two, not one: the second waits for the row lock with its connection and goes on the moment it is released, so taking a connection and the work after the commit overlap with the send in front. Measured: one conversation took 80 messages per second without the gate, 55 with two at a time, 45 with one, and three added nothing. It is an optimization of each instance's pool, not what orders sends: the row lock (decision 12) still does, on any number of instances. Gates exist only for conversations with sends in progress (a map with reference counts), so unrelated conversations never share one. Non-members are turned away before the gate (one membership query more per send), so they can't queue in front of members, as with the row lock.
24. **STOMP inbound frames and heartbeats**: inbound frames are handled on the thread that read them from the connection (`SyncTaskExecutor` on the client inbound channel), not handed to a separate pool. Spring's per-connection queue that keeps frames in order has no limit, and with a separate pool the server read frames as fast as the network delivered them: 20,000 SEND frames of 4,000 characters were read in a second and then waited in memory for minutes. Handling them on the reading thread restores TCP backpressure and keeps their order; a frame being handled occupies one of the server's request threads, as a REST request does. The simple broker offers heartbeats (`chattywap.realtime.heartbeat`, 10 s): connections that negotiate them are closed after three silent intervals, so abandoned connections (a phone that lost its network) don't stay open; clients that ask for none are unaffected.
25. **Database failures and resource limits**: a database that can't be used at the moment (no pooled connection within `POSTGRES_CONNECTION_TIMEOUT_MS`, a connection that broke, a statement that got no answer within `POSTGRES_SOCKET_TIMEOUT`) is answered with `503` in REST and STOMP (`common.DatabaseUnavailable`), logged without a stack trace; the transaction has rolled back. Measured with the defaults these replace: requests waited 30 s for a connection, and a statement on a frozen database waited until it answered. Request bodies are limited to 64 KB before Spring Security (`common.RequestBodyLimitFilter`): JSON bodies had no limit, and eight concurrent 50 MB login requests, which need no token, exhausted the heap. Sizes, timeouts and their reasons are listed in [OPERATIONS.md](OPERATIONS.md#resource-limits).
26. **Live delivery across instances: a simple broker per instance, fanned out through RabbitMQ** (resolves unresolved decision 1). Every instance keeps Spring's simple broker and its own connections, subscriptions and user registry. After the commit, `realtime.MessageBroadcaster` delivers `MessageSentEvent` and `ReceiptPositionChangedEvent` to the recipients connected to its own instance, directly and without RabbitMQ, as before (decisions 14 and 20). `messaging.RealtimeFanoutPublisher` listens to the same events after the commit and publishes them to the durable fanout exchange `chattywap.realtime`, which copies each to one queue per instance, `chattywap.realtime.<instance ID>` (a random ID per start): classic, non-durable, exclusive and auto-delete, so it exists exactly while its instance is connected, and limited to 10,000 messages, the oldest dropped first. `messaging.RealtimeFanoutConsumer`, one consumer per instance, skips the events its own instance published (their origin header) and hands the others to `MessageBroadcaster`, which delivers them like its own: the recipients' user IDs travel with the event, and each instance resolves them to its own STOMP sessions for `RecipientSessionsInterceptor`, so who receives what is decided once, when the message is stored, on whichever instance the recipient is connected to. `messaging` already depends on `realtime` (rule 7); `realtime` never sees RabbitMQ.
    - **Guarantees.** At most once and best effort per connection, as on one instance: the messages are transient and unconfirmed, never requeued or retried, and a queue goes away with its instance's connection. Each connection receives an event once: from its own instance directly, or from the fan-out, never both. Order: an instance publishes from one thread on one channel, and every instance consumes its queue with one consumer and sends to each connection in publish order, so the events committed through one instance reach every connection in commit order, wherever it is connected; one connection's messages keep their order (decision 14). Events committed through different instances interleave in any order, as events from different senders already did.
    - **RabbitMQ unavailable or blocking.** Delivery to clients on the instance that stored the event is unaffected; nothing in a request waits for RabbitMQ (decision 15). Clients on other instances don't receive the event live: the publisher drops what it can't publish, and after a failure drops events without trying for one second, so an outage costs one connection attempt per second, not one per event, and nothing is delivered minutes late. Up to 10,000 events wait in memory for the publishing thread (a broker that blocks publishers); more are dropped. Once RabbitMQ is back, the next event is published, and each consumer reconnects and declares its queue again within the listener's recovery interval (5 s); what was dropped is in the history, and sequence numbers show clients the gap (decision 17).
    - **Content in RabbitMQ.** Unlike integration events (decision 15: IDs only, durable, for consumers), the fan-out carries what clients receive: the message as the API returns it, content included, and its recipients' IDs, as JSON of the domain event. The alternative, every instance reading every message from PostgreSQL again, would cost a query per message and instance. The messages are transient, in queues that RabbitMQ deletes with their instance, but access to RabbitMQ must now be restricted like access to the database: whoever can publish to `chattywap.realtime` can deliver to clients. The format is internal to the application, but instances of two versions exchange it during a rolling deployment: changes to these events and their DTOs must stay compatible (new fields only); an event an instance can't read is dropped and counted.
    - **Cost.** Measured with two instances on one machine (1,000 connections, 20 messages per second), a delivery through RabbitMQ arrived 3 ms later at the median and 6 ms later at p95 than one from the client's own instance, and none was lost ([loadtest/README.md](loadtest/README.md#websocket-delivery-across-two-instances)). Every instance receives every event, its own included: with N instances, each message and receipt change is published once and delivered to N queues. Fine for a handful of instances; with many, binding each queue only to the conversations its instance's clients subscribed to (a topic exchange keyed by conversation) would cut that. The publisher has a connection of its own, so a broker that blocks it blocks neither the outbox relay nor the consumers.
    - **Rejected: a STOMP broker relay to RabbitMQ's STOMP plugin.** It moves the broker's work into RabbitMQ: every client connection becomes a STOMP connection from the instance to RabbitMQ and every subscription a queue there (1,000 clients with 20 conversations open: 20,000 queues). WebSocket messaging would stop altogether while RabbitMQ is down, instead of only between instances. `RecipientSessionsInterceptor`'s session IDs mean nothing outside their instance, so recipients would have to travel as STOMP headers and be filtered on the way out. It also needs Reactor Netty and the plugin, and puts a RabbitMQ connection into `realtime` (or STOMP into `messaging`), across the package boundaries above.

## Unresolved decisions

1. **STOMP broker strategy**: resolved, see decision 26 (a simple broker per instance, fanned out through RabbitMQ).
2. **STOMP authentication**: resolved, see decision 13.
3. **Outbox relay and delivery semantics**: resolved, see decisions 15 and 16. Still open: retention of published outbox rows and of `processed_events` (both grow without bound; a cleanup must keep `processed_events` rows longer than any event can still be redelivered), and whether a future consumer needs events in order (the relay publishes them in no guaranteed order).
4. **Presence storage**: per-instance memory breaks with more than one instance. The options are PostgreSQL, propagation through RabbitMQ (the fan-out of decision 26 could carry presence changes, though an instance that starts would still need the current state from somewhere), or a new store such as Redis (new dependency). Also: who may see whose presence.
5. **Boundary enforcement**: the rules are currently enforced by review and Java visibility. ArchUnit or Spring Modulith could check them in tests, but either adds a dependency.
6. **Refresh-token cleanup**: expired and revoked rows are never deleted. A scheduled cleanup must keep rotated tokens of live families, or reuse detection stops working for them.
7. **Account deletion**: users who created or belong to a conversation, or sent a message, can't be deleted (`on delete restrict`). Account deletion has to decide what happens to their conversations, memberships and messages (remove, anonymize, hand over).
8. **Retention of deleted groups**: deleted groups are kept indefinitely, including their names and messages. Whether and when they are purged is a product decision that hasn't been made; a purge has to delete the messages explicitly (`on delete restrict`).
9. **Message sequencing for real-time delivery**: history order matches commit order only on one instance with a clock that doesn't go back (decision 11). Clients subscribe first, then read the history down to the last message they have, and drop duplicates by ID; live messages from different senders can arrive in a different order than the history, so clients place them by `(createdAt, id)`. That is sound on one instance; with several, whose live delivery decision 26 provides, it holds only while their clocks agree. Messages have per-conversation sequence numbers in commit order (decision 17), which receipts use and which let clients detect gaps, also those left by live deliveries dropped between instances. Still open: whether the history should be ordered, paged and caught up by sequence number instead of `(created_at, id)`, which would make "messages since" reliable with several instances whatever their clocks. Decide together with the delivery semantics (unresolved decision 3).
10. **Receipt privacy and fan-out**: every member sees every member's receipt positions, and every change goes to every connected member, so a group of 100 can produce up to 100 frames for each acknowledgement. Open: whether members may turn read receipts off, whether groups should show receipts only to the senders of the messages a change covers, and whether delivery changes in groups should be coalesced. Positions would stay as they are; only who receives them would change.
11. **Rate limiting**: there is no per-user or per-address limit. Login and registration cost about 0.1 s of CPU each (BCrypt), and any member can send as fast as the conversation's lock allows. Limits by client address belong in front of the application (it can't see addresses behind a proxy reliably); per-user limits on sends would need shared state across instances (PostgreSQL or a new store).
12. **Queries whose cost grows with history**: page-number history pages read every message before their offset (measured: 130 ms at offset 100,000 in a conversation of 200,000; cursor pages take under 1 ms at any depth), and the unread count of a member without a read position counts every message others sent (16 ms for 200,000). Options: capping page numbers at a depth and sending clients to cursors (an API change), and an index on `(conversation_id, sender_id, sequence_number)` that would let unread counts subtract the member's own messages (one more index entry per message). Neither is needed at the sizes measured.
